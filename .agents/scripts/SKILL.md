# UI 実装・検証プロトコル

## 原則

**スクリーンショットを提示していない状態で「完了」と報告してはならない。**
実行結果を伴わない「動作するはずです」という表現を禁止する。

## 手順

### 1. 計画

変更対象の画面と影響範囲を列挙し、実装計画として提示する。
ユーザーの承認を得るまでコードを編集しない。

### 2. 実装

計画に沿って編集する。計画外の変更を行う場合は、その旨を先に告げる。

### 3. 起動

開発サーバーを起動する。すでに起動している場合は再起動不要。
起動コマンドの出力（エラーの有無）をそのまま提示する。

### 4. ブラウザ検証

ブラウザで対象画面を開き、スクリーンショットを取得する。
以下の状態を個別に撮影する。

- 通常表示
- 変更したインタラクションの実行後（開いた状態、押した状態など）
- 狭い幅（モバイル相当）での表示

### 5. 自己レビュー

取得したスクリーンショットを自分で確認し、以下を **一項目ずつ明示的に** 評価する。
「問題なし」とだけ書くことを禁止する。何をどう確認したかを述べる。

- レイアウト崩れ・要素の重なり・はみ出しの有無
- テキストの切れ・省略記号の意図しない発生
- タップ／クリック対象の大きさと周囲の余白
- 情報の優先順位が視覚的な強さ（サイズ・コントラスト）と一致しているか
- 既存画面とのトーン・余白・角丸・影・配色の整合性
- 初見のユーザーが次に何をすべきか迷わないか

### 6. 反復

問題を検出したら修正し、4〜5 を再実行する。問題がなくなるまで繰り返す。

### 7. 報告

- 冒頭に結論を 1〜3 行。
- 「確認済みの事実」と「未確認・推測」を分離して記述する。
- 実行できなかった検証がある場合は「未検証」と明記し、理由を述べる。

## 禁止事項

- 指示されていないファイルの削除・大規模な書き換え
- 既存の動作を壊す変更を、その旨を告げずに行うこと
- ユーザーへの迎合。設計上のリスクや論理的破綻は率直に指摘すること
